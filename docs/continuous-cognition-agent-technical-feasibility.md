# 面向长期服务的持续认知与主动决策智能体：技术可行性研究

> 研究日期：2026-09-07  
> 研究范围：可演化记忆、动态状态建模、规划/动态规划、主动决策，以及 B 端服务企业与 C 端场景的落地边界。  
> 结论性质：基于 2024–2026 年论文原文、正式会议论文、官方项目与规范形成的工程判断，不等同于在本项目真实业务数据上的验证结果。

## 结论先行

项目在技术上**有条件可行，值得立项**，但需要把目标定位为“面向垂直服务场景的持续状态与策略平台”，而不是短期内实现跨领域、全自主、永远正确的通用认知智能体。

边界清晰、状态有可靠数据源、动作可审计且可撤销的场景，已经具备 MVP 和试点条件；开放世界、长周期、跨系统、高风险自动执行仍属于研究问题。四个模块中，可演化记忆的工程可行性最高，动态状态与混合规划次之，主动决策的产品风险最高。

| 模块 | 当前可行性 | 可以承诺 | 不宜承诺 |
|---|---:|---|---|
| 可演化记忆 | 7/10 | 有证据、有时效、可修订的跨会话记忆；冲突、过期和删除流程 | 自动形成始终正确、永不陈旧的“用户真相” |
| 动态状态建模 | 6.5/10 | 在限定维度上持续更新带置信度和有效期的状态快照 | 从稀疏信号准确读取开放式心理、意图或因果状态 |
| 规划与决策 | 6/10 | 结构化任务图、约束求解、滚动重规划、人在环 | 让 LLM 独自完成长时域动态规划并提供正确性保证 |
| 主动决策 | 5.5/10 | 基于明确事件的提醒、建议、澄清和低风险可撤销操作 | 在开放环境中自主判断何时介入并直接执行高影响动作 |

这里的分数是项目级工程判断，不是标准 TRL 等级。判断依据是：长期记忆已有可复现架构，但 [LongMemEval（ICLR 2025）](https://proceedings.iclr.cc/paper_files/paper/2025/hash/d813d324dbf0598bbdc9c8e79740ed01-Abstract-Conference.html) 仍观察到商业助手和长上下文模型在持续交互中的记忆准确率约下降 30%；到了更接近“有经验同事”的环境经验记忆，[LongMemEval-V2（2026 预印本）](https://arxiv.org/abs/2605.12493) 的最佳方法为 72.5%，强 RAG 基线为 48.5%，且高精度方法仍有明显延迟成本。

## 四个核心模块的技术判断

### 1. 可演化记忆结构：能够搭建，难点从“存下来”转向“何时相信、更新和遗忘”

已有工作分别验证了分层记忆、反思、动态链接、合并与更新等机制：[Generative Agents](https://arxiv.org/abs/2304.03442) 将经历流、反思与规划组合起来；[MemGPT](https://arxiv.org/abs/2310.08560) 用分层存储和虚拟上下文管理跨会话信息；[A-MEM（2025）](https://arxiv.org/abs/2502.12110) 让新记忆触发历史记忆的动态链接和属性更新。2026 年正式发表的 [LightMem（ICLR 2026）](https://proceedings.iclr.cc/paper_files/paper/2026/hash/a05b72653ec5b473732129829ae04195-Abstract-Conference.html) 进一步证明，离线“睡眠期”整合可以将在线推理与长期整理解耦，并显著降低 token、API 调用和运行时间。

因此，不需要把“记忆”做成模型参数的持续训练；使用外部、可追溯、可重算的记忆层更适合产品化。建议采用以下结构：

1. **Observation Event**：只追加的原始观察与交互结果，是可追溯事实，不因后续推断而改写。
2. **Memory Candidate**：模型提出的语义解释，进入存储前先通过权限、敏感性、证据强度和重复/冲突检查。
3. **Memory Item**：带来源、主体、作用域、置信度、有效时间、最后确认时间和版本关系的可修订主张。
4. **多类记忆投影**：情景记忆保存“发生过什么”，语义记忆保存相对稳定的偏好和关系，程序记忆保存“在这个企业/用户环境中怎样做事”。
5. **Memory Mutation**：只允许 create、reinforce、weaken、supersede、merge、expire、delete 等显式变更；不做无历史覆盖。
6. **混合索引**：关键词/结构化过滤负责精确性，向量检索负责语义候选，时间索引和关系图负责时序与关联；向量库不作为事实唯一来源。
7. **Recall Bundle**：召回结果必须同时返回采用的证据、未解决冲突和因权限/时效被省略的内容。

关键限制是：外部记忆没有消除持续学习的稳定性—可塑性矛盾，只是把问题转移到了表示和检索上。2026 年研究发现，新旧经验会在有限上下文内竞争，细粒度组织不必然更好，并可能造成负迁移和遗忘（[When Continual Learning Moves to Memory](https://arxiv.org/abs/2604.27003)）。[Memora（ACL 2026 Findings）](https://arxiv.org/abs/2604.20006) 也发现多个记忆智能体仍频繁复用已经失效的记忆，难以调和变化中的信息。

删除同样必须覆盖派生摘要、向量索引、缓存和图关系，而不是只删原始记录。2026 年一项部署时记忆研究发现，只删除原文时，派生摘要中仍有约 20% 的样本可恢复被删信息；完整管道清除或墓碑式脱敏才能将最坏层级的残留降为零（[Deployment-Time Memorization in Foundation-Model Agents](https://arxiv.org/abs/2606.10062)）。

### 2. 动态状态建模：在有限维度上可行，必须把事实和推断分开

长期记忆回答“过去留下了什么”，动态状态回答“此刻最可能是什么”。两者不应共用一个无时效的用户画像。建议将决策时状态拆成：

- **Observed facts**：CRM、订单、工单、日程、传感器、用户明确陈述等可验证事实；
- **Beliefs**：对当前意图、疲劳、时间压力、打扰意愿等隐变量的概率性推断；
- **Goals and constraints**：用户目标、企业政策、预算、SLA、权限和风险上限；
- **State validity**：每一维的证据、置信度、有效期、模型版本和未知状态。

POMDP 的信念状态为“部分可观测、状态会变化、行动影响未来观测”的问题提供了严格形式基础；但在真实服务场景中完整求解通常不可行，应将其作为建模语言，而不是要求在线精确求解。2025 年的 [τ²-bench](https://arxiv.org/abs/2506.07982) 已把技术支持中用户与智能体共同改变共享环境建模为 Dec-POMDP，并发现从单方控制切换到双方控制后性能显著下降，这与真实服务中的状态同步和协作难题一致。

动态用户画像仍不成熟。[PERSONAMEM（COLM 2025）](https://arxiv.org/abs/2504.14225) 覆盖最多 60 个会话和 15 类个性化任务，前沿模型在识别随时间变化的用户画像并给出当前适配响应时总体准确率仅约 50%。因此工程上必须遵守两条规则：

- LLM 产生的状态只能进入 belief 层，不能覆盖 CRM、订单、账户权限等事实源；
- 低置信度、高影响或相互矛盾的状态应触发澄清、继续观察或保持静默，而不是强行归类。

实现上适合采用 event sourcing + reducer/materialized view：每次新事件到来后只更新受影响的状态维度，并生成带 TTL 的 `State Snapshot`。对短期状态使用规则、统计滤波、小模型或校准分类器通常比让大模型自由生成整份画像更稳定、成本也更可控。

### 3. 动态规划与主动决策者：应采用混合式、滚动时域，而不是纯 LLM 规划

“动态规划”需要先澄清为两种不同含义：

- 若指 Bellman 递推意义上的 DP，它适合状态、动作、转移和奖励都能压缩到有限规模的问题；开放式自然语言服务的状态/动作空间通常太大，不能直接穷举。
- 若指环境变化后持续重规划，更合适的是**分层任务图 + 滚动时域/MPC + 约束求解或启发式搜索**。

推荐职责分工：

1. LLM 将目标转成任务、前置条件和少量行动候选；
2. 规则引擎、权限系统、CP-SAT/PDDL 或业务工作流验证硬约束；
3. 价值模型或显式效用函数对可行动作排序；
4. 每执行一步便读取真实环境差分，更新状态并重规划；
5. 高风险、不可逆或跨主体动作进入人工审批；
6. 计划失败被记录为经验，不自动等同于用户偏好变化。

这一路线与前沿证据一致。[NL-PDDL（ICLR 2026）](https://proceedings.iclr.cc/paper_files/paper/2026/hash/d7c7b6f2e4ad3f56b85eaae765016d3a-Abstract-Conference.html) 明确指出纯 LLM/VLM 在开放世界的长时域复杂目标上仍会幻觉且缺少因果推理，传统 PDDL 又依赖完整模型；其混合表示和回归规划正是连接语义理解与可验证计划的尝试。更综合的 [AgencyBench（ACL 2026）](https://aclanthology.org/2026.acl-long.337/) 中，真实长任务平均需要约 90 次工具调用、100 万 token 和数小时，闭源模型总体也只有 48.4%，说明真正瓶颈是长程执行中的误差积累、反馈修正和资源效率，而不是一次性生成一个看似合理的计划。

### 4. 主动决策：技术上能触发，产品上最难的是“不该出现时保持沉默”

主动性不是“多发提醒”，而是对机会价值、打扰成本、权限、隐私和错误损失的联合决策。建议先执行硬约束，再比较预期效用：

`action utility = expected benefit - interruption cost - error/risk cost - privacy cost`

并将行动分为四级：

| 等级 | 行为 | 默认策略 |
|---|---|---|
| L0 | 静默记录/继续观察 | 信息不足或收益不超过打扰成本时的首选 |
| L1 | 建议或提醒 | 低风险、有明确证据、用户可忽略 |
| L2 | 请求确认/澄清 | 状态不确定、涉及外部写入或中等影响 |
| L3 | 自动执行 | 仅限已授权、可撤销、可审计且通过场景门禁的动作 |

[ProactiveBench（ICLR 2025）](https://proceedings.iclr.cc/paper_files/paper/2025/hash/75c37811e830bf029584b1c6fac17726-Abstract-Conference.html) 证明主动援助能力可以通过专项数据训练，但其最佳专项模型 F1 为 66.47%，仍意味着明显误报和漏报。[π-Bench（2026 预印本）](https://arxiv.org/abs/2605.14678) 进一步显示“完成任务”和“主动发现隐藏需求”是两种不同能力；[ProEvent（2026 预印本）](https://arxiv.org/abs/2607.17701) 则发现现有智能体会过度行动，并难以处理事件取消，在其设置中 GPT-5.1 仅在 26.7% 场景中反应正确。

因此主动系统必须把 `Silent Action` 作为显式候选，并单独测量过度打扰率、漏报率、确认率和撤销率，而不能只用任务完成率评价。

## 推荐的端到端系统结构

```text
多源事件流
  ↓  身份/租户/权限校验 + 数据最小化
不可变 Observation Event 日志
  ├─→ 记忆候选抽取 → 冲突/时效/敏感性策略 → 可演化 Memory Store
  └─→ 状态 reducer / belief updater → 带证据和 TTL 的 State Snapshot
                         ↓
Decision Context = 当前事实 + 状态信念 + Recall Bundle + 目标/约束
                         ↓
候选生成器（LLM/规则）→ 硬约束过滤 → 计划器/价值排序
                         ↓
静默 / 建议 / 请求确认 / 受限自动执行
                         ↓
Decision Record + 执行回执 + Feedback Event → 状态与记忆的受控更新
```

这个架构的关键不是选择某个“大一统 Agent 框架”，而是保持五条系统不变量：

1. 事实源、状态推断和长期记忆三者分层；
2. 每次召回、决策和外部动作都有证据与版本号；
3. LLM 不能绕过确定性的权限和业务政策；
4. 写操作必须幂等，高影响动作可暂停、审批、补偿或撤销；
5. 反馈只记录“发生了什么”，不能把忽略或拒绝直接解释成永久偏好。

外部工具数据还会形成新的攻击面。[AgentDojo（NeurIPS 2024）](https://proceedings.nips.cc/paper_files/paper/2024/hash/97091a5177d8dc64b1da8bf3e1f6fb54-Abstract-Datasets_and_Benchmarks_Track.html) 在 97 个工具任务和 629 个安全测试中显示，工具返回内容可通过间接提示注入劫持智能体，现有攻击与防御都不可靠。因此检索内容、网页、邮件和历史记忆均应视为不可信数据，外部动作需要模型之外的策略执行点。

## B 端与 C 端落地判断

### B 端服务企业：更适合作为第一落地点

B 端具有结构化事实源、明确角色权限、可量化 KPI 和重复工作流，技术可验证性更强。优先级建议如下：

| 优先级 | 场景 | 自动化边界 |
|---|---|---|
| P0 | 工单分诊、信息补全、SLA/续约风险提醒、客户成功 next-best-action | 只读分析或建议，人工确认写入 |
| P1 | 跟进计划、销售/服务材料准备、跨会话客户上下文总结 | 可自动生成草稿，发送和关键字段变更需确认 |
| P2 | 标准化低风险流程执行 | 仅对幂等、可撤销动作自动执行 |
| 暂缓 | 定价、退款、合同承诺、权限变更、敏感客户信息跨团队共享 | 保持人在环和确定性政策校验 |

现实差距仍很大。[CRMArena-Pro](https://arxiv.org/abs/2505.18878) 覆盖销售、客服和 CPQ 的 B2B/B2C、多轮与保密场景，领先智能体约为 58% 单轮成功、35% 多轮成功，且天然保密意识接近零；其[官方项目](https://github.com/SalesforceAIResearch/CRMArena) 说明论文已于 2026 年被 TMLR 接收。[τ-bench（ICLR 2025）](https://proceedings.iclr.cc/paper_files/paper/2025/hash/1b126cc38b8638e07bef37e7b2bb72bf-Abstract-Conference.html) 在零售和航空客服的动态对话、API 和政策环境中也发现，当时的 GPT-4o 任务成功率低于 50%，零售 `pass^8` 低于 25%。这些结果支持“从窄流程、建议模式和人工审批开始”，不支持直接替代服务团队。

### C 端：可以落地，但信任、隐私和打扰比模型能力更决定成败

优先选择高频、低风险、收益易被用户感知的场景：日程与旅行计划维护、提醒、信息整理、学习或健身教练、个性化推荐。默认采用“建议优先、用户确认”，避免早期进入支付、医疗诊断、法律决定或涉及他人的隐私操作。

必须具备：

- 明确 opt-in，并按数据类型分别授权读取、写入和主动触达；
- 用户可见的记忆中心，可查看来源、更正、暂停使用和彻底删除；
- 敏感属性默认不推断、不长期保存、不跨主体共享；
- 区分账户、设备、家庭成员和工作/生活作用域，防止主体混淆；
- 支持“本次不需要”“今天别提醒”“永久偏好更正”等不同强度反馈；
- 主动触达设置频控、安静时段、撤销和一键关闭。

这不是附加合规工作，而是技术正确性的一部分。NIST 的 [Generative AI Profile（NIST AI 600-1）](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence) 要求在生命周期中持续治理、测量和管理有效性、安全、隐私、透明度等风险；长期记忆和主动行动会把这些风险从单次回答扩展到长期数据与真实动作。

## MVP 路线与验证门禁

### 阶段 1：记忆与状态闭环（8–12 周量级的窄域原型）

- 接入 1–2 个可靠事件源；
- 完成事件日志、记忆变更、冲突、过期、召回解释和状态 TTL；
- 只输出建议或静默，不执行外部写操作；
- 建立时间切分的离线数据集，防止训练/评测泄漏。

门禁：关键事实来源可追溯率 100%；敏感信息越权写入/召回为 0；失效记忆误用率、冲突漏检率、状态校准误差达到场景阈值。

### 阶段 2：受控主动决策

- 加入事件触发器、行动候选、打扰成本和请求确认；
- 只开放低风险、可忽略、可撤销的触达；
- 进行影子运行：系统给出决策但不真正触达，用人工或历史反事实判定。

门禁：禁止行动与权限违规为 0；过度打扰率和错误确认率低于业务阈值；相对 Memory-only 模式有显著增益。

### 阶段 3：有限自动执行

- 对少量幂等流程启用工具写入；
- 使用事务、幂等键、审批、超时、重试上限和补偿动作；
- 持续红队测试提示注入、记忆投毒、越权和跨租户泄漏。

门禁：按 `pass^k` 而非单次成功率评估稳定性；所有写动作可审计；高影响失败可恢复；异常时 fail closed。

评测至少需要三组对照：只看当前上下文的 Baseline、只增加记忆的 Memory Mode、加入动态状态与受控主动决策的完整模式。除任务成功率外，应同时报告记忆新鲜度、状态校准、政策违规、打扰率、确认率、撤销率、延迟、token/调用成本和人工接管率。

## 主要风险与缓解

| 风险 | 为什么关键 | 建议缓解 |
|---|---|---|
| 陈旧/错误记忆累积 | 错误会跨会话放大并影响后续行动 | 证据链、有效期、冲突集、显式替代、删除全链路测试 |
| 状态与记忆混淆 | 暂时状态会被错误固化为人格或永久偏好 | 分层 schema；状态 TTL；低置信度不入长期记忆 |
| 长程误差累积 | 每一步的小错误会在多工具、多轮计划中放大 | 滚动重规划、短事务、检查点、验证器、人工接管 |
| 主动过度或错过 | 直接损害信任，也可能形成业务/安全损失 | 显式静默候选、打扰成本、频控、分级授权、影子评测 |
| 隐私与主体混淆 | 长期记忆更容易形成敏感推断和跨人泄漏 | 租户/主体隔离、最小化、用途限制、用户记忆中心 |
| 提示注入与记忆投毒 | 不可信工具输出可能污染长期状态并驱动未来动作 | 输入数据与指令隔离、模型外策略点、写入门禁、来源信誉 |
| 评测虚高 | 静态问答分数不能代表长期服务可靠性 | 时间切分、状态级验证、反事实对、`pass^k`、真实用户试点 |
| 成本和延迟失控 | 主动监测、重检索和树搜索会持续消耗资源 | 事件驱动而非全时轮询；小模型分流；离线整合；预算上限 |

## 与当前仓库的衔接

仓库现有设计方向与推荐架构高度一致：`CONTEXT.md` 已将 Observation Event、Memory Item、State Snapshot、Decision Context、Decision Record、Memory Mutation、Conflict Set、Recall Bundle 和 Silent Action 分开；Memory Engine 已有 `observe/recall` 接口、PostgreSQL Adapter、敏感权限、冲突与 supersede 测试。

这意味着下一步不应推翻现有模型，而应沿以下顺序深化：

1. 将确定性样例扩展为带时间漂移、矛盾证据和多主体的数据集；
2. 把状态更新从整表生成改为逐维 reducer，并补充校准评测；
3. 为行动候选加入硬约束层、打扰成本、审批级别和补偿动作；
4. 增加端到端状态验证、长期回放、提示注入和全链路删除测试；
5. 先选择一个 B 端窄流程和一个 C 端低风险场景做双轨验证，不同时扩张行业和自主级别。

## 最终判断

项目真正的创新点不应表述为“让大模型拥有记忆并自动调用工具”，因为这些组件已经可以搭建；更有价值、也更可验证的技术主张是：

> 在长期服务中，用可追溯、可修订的记忆形成持续认知，用带不确定性和时效的状态表示当前处境，再由受约束、可审计、能选择沉默的决策机制给出分级主动行为。

这个方向在垂直场景中技术可行，且现有原型已有正确的概念底座。立项时应把“长期一致性、状态校准、主动克制和安全执行”设为核心研究指标；若将成功标准设为通用、跨域、全自主智能体，则以 2026 年的公开证据看仍不可行。
